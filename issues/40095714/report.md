What went wrong?

In release build the crash happens in the following code:

```

	bool Object::IsNumber() const {
	  if (IsSmi()) return true;
	  HeapObject this_heap_object = HeapObject::cast(*this);
	  Isolate* isolate = GetIsolateForPtrCompr(this_heap_object);
	  return this_heap_object.IsHeapNumber(isolate);  <---- [1]
	}

```

At [1] we will verify if the object type is a HEAP_NUMBER_TYPE (0x41), by checking the disassembly when the crash happens we have the following instructions:

```

	00007ff6`e9aa9a10 488b49ff             mov     rcx, qword ptr [rcx-1]    <----------- [2]
	00007ff6`e9aa9a14 6683790b41           cmp     word ptr [rcx+0Bh], 41h ds:00000085`03b007e4=????  <---------- [3]
	00007ff6`e9aa9a19 7565                 jne     d8!v8::internal::CompilationCacheTable::Age+0x110 (00007ff6`e9aa9a80)

```

At [2] we will load the HeapObject map into RCX, let's check contents of (RCX-1):

As we can see, the HeapObject map (00000085`03b007d9) is currently pointing into not mapped memory, leading to an invalid address read and crash. ### ul...@chromium.org (2019-07-16)

Summary:
- The first compilation of the function produces feedback metadata with 17 slots.
- JSFunction is created with feedback vector of length 17.
- GCs happens.
- The bytecode array and feedback metadata is flushed in one of the GCs. The feedback vector is not flushed.
- The function is compiled again. This time the feedback metadata has 19 slots.
- The function with the old feedback vector of length 17 is executed and we have out-of-bounds access when updating slot #18.

Leszek told me offline that this is a known issue with parser being non-deterministic: https://bugs.chromium.org/p/v8/issues/detail?id=8510#c38 The fix might be tricky and not backmergable.

So we need a quick workaround for merging back. Ross, any ideas on how to fix it in bytecode flushing?

[Compile] Ensure we don't reuse a feedback vector with a different layout than expected.

If we flush the bytecode from a SFI we might recompile a JSFunction while the function
still has its old feedback vector. This should usually be fine since the new and old
feedback vectors have the same layout, however some bugs in the parser mean that it's
possible for eagerly and lazily compiled eval functions to have different bytecode and
so potentially different feedback vector layouts.

For now reset the feedback vector if it doesn't have the same size when we compile the
JSFunction, and recreate a new one of the correct layout. This will be replaced with a
CHECK once the parser bugs are fixed.
