## Description

**VULNERABILITY DETAILS**  

Using vulnerabilities in cups, shill, and insecure upstart configuration files, it was found to be possible to obtain root command execution in Chrome OS.  

This vulnerability chain requires manual installation, and is likely not automatable without substantial browser exploitation due to the requirement to submit print jobs and connect to a VPN. The independent privilege escalation vulnerabilities could be used as part of a separate chain.  

This chain works from Guest mode. The current root payload (ssh daemon) is not usable from guest mode because it is not possible to install the secure shell extension, however the daemon persists into other sessions and can then be connected to.

[ Overview ]  

Using a malicious PPD file and PDF it is possible to execute commands inside the restricted cups environment  

The cups init file does not check for symlinks when creating and chowning the cups configuration directories  

Therefore, the command execution can take ownership of any directory by replacing a cups directory and waiting for the service to restart

By taking ownership of the shill openvpn configuration file directory, the command execution can overwrite the openvpn configuration files.  

A malicious username specified in shill can inject newlines into the openvpn management interface to send a SIGHUP signal and cause openvpn to reload it’s configuration file.  

A well timed reload can cause openvpn to reload a maliciously planted configuration file dropped by the cups command execution

This results in root command execution. Soon it will result in shill:shill command execution.

Shill can use it’s EmitEvent upstart privileges to trigger an ARC init script which will unconditionally enter the namespace of an attacker provided PID.  

Using nested user namespaces an attacker can craft a namespace with a malicious binary at a location executed by the init script, resulting in root command execution.

[ Cups command execution ]  

The custom ChromeOS version of cupstestppd does not filter cupsPreFilter [9] as strictly as it does cupsFilter{,2} [10].  

The cupsPreFilter option as specified in a PPD file can be used to set the full path to a filter binary, which is called with uncontrollable parameters, along with a path to the print job pdf file, as generated by Chrome before being sent to cups. [0]  

By specifying the /usr/bin/dc binary (‘an arbitrary precision calculator’), it was found to be possible to execute shell commands using the ‘!’ command available inside dc. dc will iterate across all arguments and attempt to execute them as files containing instructions, not exiting if a file does not exist. Argv[6] as passed to dc is the pdf file of the printed page.  

The majority of the text contents of a pdf file are stored as binary data, but links specified in the page are stored in plaintext /URI parameters, such as the following:

/URI (<http://example.org/>)

dc will continue execution if invalid characters are specified. Using this, it is possible to construct a webpage that, when printed, executes a shell command through dc. The relevant dc commands are as follows:

q - Immediately exit dc  

[string] - push ‘string’ onto the program stack  

x - evaluate the item on the top of the stack  

! - run a shell command.  

Therefore, [!id]x will run the ‘id’ shell command.

The following html page will cause the dc command to execute the payload. The payload has been chosen to execute the PPD file (an environmental variable configured by cups) as a shell script. An initial ] closes the dc string delimiter opened by the PDF file structure, and the repeated A padding characters remove the ‘q’ character from the first binary section in the PDF, to ensure that the payload does not quit early.

data:text/html,<a href="hxxp://][!/bin/sh ${PPD} &]x">AAA</a>

For unknown reasons, directly printing this URL does not trigger the exploit reliably. First printing to PDF and then printing the resultant PDF reliably triggers the command execution.

Commands executed using this method are run as cups:root, with a very restrictive seccomp policy [1][2].

Chain Steps:  

Download malicious PPD file (exploit.ppd)  

Install malicious PPD file (snippet 2)  

Browse to and print malicious page (datauri.pdf)  

Wait 5 minutes for cupsd to stop (I am unsure why it automatically terminates). Top in crosh can be used to view the cupsd process and know when it has exited (oCOMMAND=cupsd will filter the command for cupsd in top)

[ Seccomp breakout, root/shill command execution ]  

The cupsd.conf upstart init file does not validate that directory targets are not symlinks before changing their permissions to be writable by the cups user. The cups user can therefore replace the directory /var/spool/cups/tmp with a symlink to a directory which, when cups is restarted, will be chowned to cups. Files inside this target directory can then be replaced by the cups user.

The /run/shill/openvpn\_config directory was found to be an acceptable target for exploitation. This is the directory in which shill stores OpenVPN configuration files, under randomized names, when connecting to an OpenVPN VPN. After cups has been restarted, the cups user can make this directory world writable (so shill can still write to it), and wait for an OpenVPN configuration file to appear, at which point it can be replaced. It is necessary for the directory to exist before the chowning occurs, therefore connecting to any OpenVPN first will be required. The connection need not be successful.

I was not able to directly exploit this race condition such that the OpenVPN binary uses the wrong configuration files since the timing is very tight.

Shill controls the OpenVPN process using the management interface. This management interface includes the ‘signal’ function, which sends standard unix signals (USR, HUP) to the main OpenVPN process. The SIGHUP signal causes OpenVPN to reload its configuration file without restarting the process, which would cause shill to bail and delete the configuration file.

It was found that the shill OpenVPN management server does not escape the username when sent to the OpenVPN process [4], which allows for the injection of newline characters onto the wire.

Restrictions:  

If the commands specified are malformed, OpenVPN will exit.  

If the credentials are passed are correct, the connection will succeed and OpenVPN will drop it’s privileges to openvpn:openvpn.  

If the OpenVPN server does not exist, OpenVPN will exit.  

If the signal command is sent too close to the shill configured credentials, OpenVPN will exit.

Therefore it is necessary that a valid OpenVPN server is configured, but that the provided credentials are incorrect. It was also found to be necessary to specify a large number of nop commands between the credentials and the signal command, to ensure that the OpenVPN management interface interprets them separately. The ‘test’ command in the management interface outputs a single test line to the log, and is used as the nop command.

Snippet 3 contains a configuration function to add a VPN which meets the requirements, and will trigger the SIGHUP signal at an appropriate time.

While the OpenVPN binary is being started, and the nops are being executed via the management interface from shill, the cups command execution is spinning on the /run/shill/openvpn\_config directory, waiting for the OpenVPN configuration file to appear. As soon as it appears it can be replaced with a malicious configuration file, such that when OpenVPN receives the SIGHUP an attacker controlled configuration file is loaded. The ‘tls-verify’ configuration option can be used to execute a command early in the connection process.

Currently, this results in unrestricted root command execution. However, as of shill commit 11c823c, OpenVPN is now run as shill:shill [5].

Chain Steps:  

4. Install malicious OpenVPN profile (snippet 3)  

5. Connect to OpenVPN profile. Expect failure, this is just to create /run/shill/openvpn\_config  

6. Print the same file again. This will spin on /run/shill/openvpn\_config. If the print job returns immediately with an error, exploitation has failed. Retry. Print job should hang until OpenVPN has errored out/connected. Logging is available at file:///tmp/exploit.log  

7. Connect to OpenVPN profile

[ Shill privilege escalation ]  

Shill can EmitEvent [6] on the Upstart Dbus API. We can use this to trigger the arc-sensor [7] upstart job by emitting the ‘start-arc-sensor’ event. CONTAINER\_PID is specifically imported by this upstart config file, and can therefore be passed in by shill.  

The pre-start script does not validate the CONTAINER\_PID environmental variable passed in, and executes binaries from inside this namespace as root. Using user namespaces we can create a mount namespace, which allows for creating a fake root file system by bind mounting key directories (/bin /lib64 /etc /usr/bin /tmp /proc). A nested user namespace can then pivot root into this fake root directory. If this second level user namespace process is used as the target CONTAINER\_PID, an attacker controlled /system/bin/mknod (for example. [8]) is executed as jailed root.

If mknod in this namespace is a bind mount of /bin/sh, and a file exists at CWD (/) named ‘0700’, this script will be run as root. The ‘-m’ flag is passed to sh but does not impact the execution of the payload. If the nested container has the /sys/fs/cgroup/freezer path bind mounted from the real root namespace, privilege escalation to full unrestricted root can be obtained by using the notify\_on\_release and release\_agent files, along with a maliciously constructed freezer directory.

If notify\_on\_release is set to 1, the binary specified in release\_agent is executed when a freezer’s task list becomes empty, generally to aid in cleaning up freezers. The full relative freezer path is specified as the argument, and it is possible to nest freezers. Therefore, creating a freezer named tmp, with a nested freezer named exploit.sh, writing /bin/sh to release\_agent and a payload to /tmp/exploit.sh will cause the script to be executed when the inner exploit.sh freezer tasklist becomes empty. A short lived sleep was used to exploit this quickly. The resulting command execution is in the default namespace without restrictions.

A full proof of concept script has been attached as shillprivesc.sh, which will bind mount a setuid shell over ‘top’, so that exploitation can be accessed from crosh.

For verification purposes, the following minijail0 command should emulate the privileges used in [4]

sudo /sbin/minijail0 -c 0x30c0 -u shill -g shill -- /bin/sh

[ Attachments ]  

Exploit.ppd - PPD file, containing a short shell script which either creates the /var/spool/cups/tmp symlink, or spins and replaces the openvpn configuration, depending on which print run it is executed from. This file also contains a base64 encoded statically compiled dropbear binary with hardcoded credentials root:EXPLOIT, as a sample post exploitation payload. This is what will be run as root upon successful exploitation. This file also configures the cupsPreFilter.

Datauri.pdf - the resultant PDF from printing the data URI in Snippet 2. The contents contains the payload ‘sh ${PPD}’ as can be seen in the text editor. This triggers the exploitation of /usr/bin/dc

Shillprivesc.sh - The currently unneeded privilege escalation from the shill user, which will be chained after the openvpn exploitation upon update.

Cupstestppd\_pathrestriction.patch - A patch for third\_party/cups [11] which copies the path restriction code from cupsFilter and applies it to cupsPreFilter. This patch is untested.

openvpn\_management\_server\_EscapeToQuote\_username.patch - A patch for platform2 [12] which copies the use of EscapeToQuote from the password sending function to the user sending function. According to the OpenVPN documentation the username and password commands are the same so this usage should mitigate the issue. This patch is also untested.

Cupsd\_init\_symlink.patch - A patch for chromiumos-overlay [13] to include a symlink check, taken from cryptohome’s init script [14]. This patch is also untested

Server.conf - A minimal openvpn server configuration file. Valid certificates must be configured and trusted on ChromeOS. (I used standard LetsEncrypt certificates without issue)

### ro...@rorym.cnamara.com (2018-09-17)

There is no explicit vulnerability in OpenVPN, no.

OpenVPN allows for command execution by design in the configuration file. The vulnerability here is that the username field can inject newlines into the management interface (a shill escaping issue), and the 'signal' command reloads the configuration file from disk.

Removing 'signal' in the management interface may be a worthwhile hardening patch, since it may be exploitable in future from other shill exploitation (OpenVPN management interface maintains a persistent socket with shill, so shill can in theory always send new commands).
