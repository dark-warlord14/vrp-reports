## Description

VULNERABILITY DETAILS

Heap-buffer-overflow in blink::FFTFrame via WaveShaperNode oversampling with non-power-of-2 renderSizeHint

VERSION
Chrome Version:146.0.7670.0

Operating System: Linux, Debian

REPRODUCTION CASE

```
<!DOCTYPE html>
<!--
 ./chrome --enable-features=WebAudioConfigurableRenderQuantum
-->
<script>
  try {

    const ctx = new AudioContext({
      renderSizeHint: 57456, 
      latencyHint: 'playback'
    });

    const shaper = ctx.createWaveShaper();


    shaper.connect(ctx.destination);



    shaper.oversample = '4x'; 

  } catch (e) {
    console.error(e);
  }
</script>

```

Type of crash: renderer
Crash State: asan.txt (attachments), also llvm.txt generated by `llvm-symbolizer --obj=/home/davi/chromium-asan/chrome 0x3b84dc3d 0x3ba46be4 0x3ba47adf 0x3ba3fb38 0x3ba3edbb 0x3ba3c651 0x3a5b6b58 0x166a18be 0x166a00ac 0x17836e1c 0x1783dae4 0x178317c6 0x1702fb49 0x17046d82 0x1b5c5f75 0x1b514829 0x1b5115db 0x1b51132a 0x16a1b716 0x16a1de13 0x16572898`

### mj...@google.com (2026-02-17)

fft\_frame\_pfft contains a [set number of predefined sizes](https://crsrc.org/c/third_party/blink/renderer/platform/audio/pffft/fft_frame_pffft.cc;drc=6d3e2ca997ca3ef995f719b22a1658a250a22d1e;l=42) -- we have some DCHECKs in place but these should probably be changed to CHECKs to catch this sort of problem with a crash instead of letting it through.

We should also update the FFT implementation to work with non-power-of-two sizes (probably by zero padding the input), but that is out of scope for this issue.

My plan is to convert FFTFrame DCHECKs to CHECKs and add additional CHECKs, which should be sufficient to resolve the security issue.

This feature is enabled in OT from M145, and disabled otherwise. Currently identified OT partners are not using the WaveShaper node. The OT is in open registration. It's possible that other OT participants could try to use this node, but only on origins they control.

Assigning temporarily to Martin to evaluate the security impact given the above, then please assign back to me so I can track adding the CHECKs to the code.

### ma...@google.com (2026-02-17)

OT counts as available in Stable in this case. And that you need to control the origin that enables the OT isn't really a mitigating factor. So I think we should treat this as if this feature was fully launched on Stable.

### mj...@google.com (2026-02-17)

Thank you for confirming. Here is the plan:

- Change all DCHECKs to CHECKs in the initialization functions for the following:
  - <https://crsrc.org/c/third_party/blink/renderer/platform/audio/fft_frame.cc>
  - <https://crsrc.org/c/third_party/blink/renderer/platform/audio/pffft/fft_frame_pffft.cc>
  - <https://crsrc.org/c/third_party/blink/renderer/platform/audio/mac/fft_frame_mac.cc>

This includes anything that runs on the main thread, but not `DoFFT` or `DoInverseFFT`.

Then, we should also add additional CHECKs in the constructors that `fft_size` is between the minimum and maximum allowed values:

- <https://crsrc.org/c/third_party/blink/renderer/platform/audio/pffft/fft_frame_pffft.cc;l=119>
- <https://crsrc.org/c/third_party/blink/renderer/platform/audio/mac/fft_frame_mac.cc;l=92>

This should be enough to change the overflow into a crash, thus mitigating the security issue. I will file a separate issue to implement non-power-of-two handling.

Note that the OT is only available from M145 onwards, so while this issue was found in M144 using the command-line switch it is only exposed to stable in M145 and we thus should only have to merge back to M145 and M146. Unfortunately M145 is already shipping to stable, so we will try to resolve this quickly.
