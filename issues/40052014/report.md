### ro...@google.com (2020-04-16)

I don't think it's actually a Mojo internals issue. We just land there after memory has been corrupted or misused.

This looks like a UAF on the SmsFetcher referenced by an SmsService. I believe it was introduced by https://chromium.googlesource.com/chromium/src/+/dbdd5c9645de96

Prior to that CL, it was true that the singular SmsFetcherImpl instance was created lazily and lived as long as the BrowserContext. This behavior is assumed by the comment here[1] justifying use of a raw SmsFetcher* as a member of SmsService.

Since that CL has landed, SmsFetcherImpl objects can be replaced arbitrarily when Get() is called if the previously stored fetcher returns false for CanReceiveSms(). The comment is thus no longer true and SmsService objects can end up holding onto a freed SmsFetcher*.

[1] https://cs.chromium.org/chromium/src/content/browser/sms/sms_service.h?rcl=c1749f8f66e4bd78f79ef1cb16e41c63dbafbb49&l=75

This changes SmsProviderGmsUserConsent from holding a WeakPtr
of RenderFrameHost to having RenderFrameHost be passed by
the SmsService and only used upon Retrieve(). SmsService is
connected to the RenderFrameHost lifecycle and will be destroyed
upon frame destruction.
